# Архитектура

## Состав

React + TypeScript + Vite отвечают за интерфейс. Express + TypeScript — за API, базу и подключение модели. Zod проверяет входные и выходные данные. Vitest/Supertest проверяют сервер; Playwright — браузерные сценарии. Версии фиксируются в package-lock.json.

```text
CRM UI (React)
  ├─ История → localStorage браузера
  ├─ GET/PUT /api/knowledge → KnowledgeStore → data/knowledge.json
  └─ POST /api/generate → generateAdvice
                            ├─ demoAdvice (явные правила)
                            └─ OpenRouter / Yandex REST API (настоящая модель)
                                   ↓
                            validateAdvice
                                   ↓
                      Ответ + внутренняя подсказка + источники
```

Сервер берёт собственную актуальную базу, а не доверяет фактам, переданным браузером. При малом объёме вся база идёт в контекст: отдельные embeddings и векторное хранилище не нужны. Менеджерские реплики имеют отдельную роль `manager` в данных диалога; они не подменяют инструкции модели.

## Контракты

`GET /api/health`: provider (`demo`/`yandex`/`openrouter`), configured, model (публичное название), version. configured означает наличие параметров, а не проверку ключа.

`GET /api/knowledge`: `{revision, entries}`. Запись: `{id, kind, title, text, price, maxArea}`. null у цены означает отсутствие фиксированной цены, у maxArea — неприменимость.

`PUT /api/knowledge`: передаёт полную базу с текущей revision. Сервер валидирует, проверяет конфликт версий, записывает временный файл и атомарно заменяет рабочий. Версия увеличивается только после успешной записи. Записи в одном процессе сериализованы.

`POST /api/generate`: `{revision, messages:[{id,role,text,at}]}`. В ответе:

```json
{
  "answer": "Вежливый черновик клиенту",
  "intent": "selection",
  "upsell": {
    "status": "offer",
    "title": "Стандартный монтаж",
    "reason": "Почему предложение подходит",
    "phrase": "Фраза для менеджера",
    "itemId": "installation"
  },
  "sourceIds": ["comfort-07", "installation"],
  "missing": ["Условия установки"],
  "mode": "yandex",
  "revision": 1,
  "durationMs": 1000
}
```

Показанный JSON иллюстрирует контракт, а не результат реальной модели. Статусы допродажи: offer, skip, clarify. Intent: selection, question, support, clarification.

Ошибки: 400 (невалидные данные), 403 (внешний origin/host), 409 (база изменилась), 413 (слишком большой запрос), 429 (лимит), 502 (сеть/ответ провайдера), 503 (не настроен ключ), 504 (таймаут), 500 (прочая ошибка сервера). Ошибочные тела провайдера и ключи не выводятся пользователю.

## Актуальность

При сообщении клиента или менеджера результат этого диалога удаляется. После сохранения базы удаляются все результаты. При переключении диалога запрос отменяется; поздний ответ не применяется к другому клиенту. Если база меняется во время генерации, сервер возвращает конфликт вместо устаревшего результата. При внешнем изменении базы другой вкладкой текущая вкладка узнаёт о конфликте при следующем запросе, после чего можно обновить базу.

Несохранённые ручные черновики требуют проверки менеджера, сохраняются в памяти до перезагрузки и не отправляются автоматически. Несохранённые изменения базы защищены подтверждением при уходе и beforeunload при закрытии вкладки.

## Защита и ограничения

- Ключ только в переменных окружения сервера; `.env` исключён из Git.
- UI выводит строки через React без HTML-инъекций.
- JSON-схемы ограничивают роли, размеры, типы и записи.
- Системный промпт отделяет данные переписки от инструкций, запрещает выдуманные факты и повторные продажи.
- Сервер проверяет существование источников, предложение из товарной/сервисной записи и совпадение отдельных сумм с ценами в базе/парными суммами. Это ограниченная эвристика, не семантическое доказательство.
- Отдельные эвристики подавляют допродажу при распознанной жалобе или отказе. В сложном языке возможны ошибки, требуется проверка человеком.
- Таймаут OpenRouter 60 секунд, Yandex 25 секунд; клиента 65 секунд. Никакого скрытого fallback в demo.
- Данные клиента не логируются сервером. В live-режиме диалог и база уходят выбранному провайдеру: OpenRouter или Yandex; содержимое демо вымышлено.

## Подключение AmoCRM позднее

Сохранить `generateAdvice` и контракт двух блоков. Вместо симуляции добавить адаптер получения истории из CRM, отображение подсказки менеджеру и явное действие для вставки согласованного текста. Конкретные способы встраивания, права и авторизацию проверить по актуальной документации AmoCRM после уточнения требований работодателя. Реализация интеграции в этом этапе отсутствует.

## Размещение позднее

Текущий сервер сознательно слушает только localhost; локальные проверки Host/Origin рассчитаны на него. Перед публикацией нужны настройка домена/HTTPS, авторизация и права на редактирование базы, разрешённые origin, лимиты на пользователя, резервное копирование, нормальное серверное хранилище истории, production-процесс и тест доступности из РФ. Обходить локальные ограничения простой публикацией порта нельзя считать завершённым деплоем.

OpenRouter использует строгую JSON Schema. Все endpoint ограничены нулевой ценой. При 401 допускается одна попытка резервным ключом; при 429, 402 и других ошибках перебора ключей нет. Денежная проверка допускает числовой бюджет только с явным словом «бюджет» и совпадением с бюджетом клиента; это не разрешает подставлять его как цену товара.
